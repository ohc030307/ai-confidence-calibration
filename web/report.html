AI는 언제 자신 있게 틀리는가

ENG3510 인공지능을 위한 데이터분석 기말 프로젝트 결과보고서 · 오현철 · 2026년 12월
GitHub: github.com/ohc030307/ai-confidence-calibration (문항, 코드, 모든 원본 응답)

요약. AI가 답과 함께 말하는 확신도가 실제 정답률과 맞는지를, 정답이 하나로 정해지는 수학·컴퓨터 문항 141개로 측정했다. Claude 3개 모델(Haiku·Sonnet·Opus 5.5)은 문항마다 3번, Gemini 2개 모델(3.5 Flash·Flash-Lite)은 무료 한도 안에서 기본 81문항을 1번씩 물었다. Claude는 확신도가 정답률과 가까웠고 오히려 약간 낮게 말했지만(ECE ), 쉬운 문항에서 한 번씩 실수하고도 98~99%라고 답한 경우가 있었다. Gemini Flash-Lite는 기본 문항 정답률 인데 모든 응답의 확신도가 100%였다. 개선 방법으로 (1) 검산을 시키는 점검 프롬프트는 확신도 90% 이상인데 틀린 응답을 건에서 건으로 줄였고(다만 처음 건수가 적어 우연일 가능성은 남는다), (2) 같은 질문을 3번 물어 답이 다르면 표시하는 방법은 그런 응답 를 모두 잡아냈다. 실험 결과와 함께, 대학생이 분야별로 AI 평점·후기를 남기는 게시판을 웹사이트로 공개했다.

1. 문제

사람은 AI의 확신도를 보고 검산할지를 정한다. "99% 확신한다"는 답은 그대로 쓰고, "60% 정도"라는 답은 다시 확인한다. 그러므로 확신도가 실제 정답률과 맞지 않으면, 사람은 AI가 틀렸을 때 오히려 가장 강하게 믿게 된다. 2026년 11월 세무사 시험 수석 합격자가 초소형 카메라와 생성형 AI로 시험을 쳤다고 자백하고, 법학적성시험에서 AI 스마트안경 부정행위가 적발되면서(BBC 코리아 2026.11.19, 연합뉴스 2026.11.17), "AI가 알려 준 답을 확인 없이 쓰는 상황"은 더 이상 가정이 아니게 되었다.

10월 예비 시험(20문항, 1회)에서 Gemini는 16문항을 맞히면서 틀린 4문항을 포함해 모든 문항에 확신도 100%를 말했고, Claude는 20문항을 다 맞히며 90~99%를 말했다. 20문항 1회로는 결론을 낼 수 없어, 다음 세 질문을 본 실험으로 확인했다.

  • Q1. AI가 말한 확신도는 실제 정답률과 맞는가?
  • Q2. 어떤 문제에서 자신 있게 틀리는가?
  • Q3. 자신 있게 틀리는 경우를 줄이는 방법이 있는가?

1.1 기존 서비스와의 차이

"어떤 AI가 좋은가"를 알려 주는 곳은 이미 있다. There's An AI For That은 하는 일별로 AI 도구를 찾고 사용자 평점을 보는 영어권 디렉터리이고, Arena(구 LMArena)는 같은 질문에 대한 두 AI의 답에 사람이 블라인드로 투표해 모델 순위를 매긴다. 국내에는 대학생용 AI 추천 기사(링커리어, 대학내일 등)와 커뮤니티 게시글이 있다. 그러나 앞의 둘은 답이 좋아 보이는지를 재고, 뒤의 것은 개인 경험을 모은다. AI가 스스로 말한 확신도를 실제 정답과 맞춰 보는 측정은 찾지 못했고, 한국 대학생이 전공별로 평가를 남기는 곳도 찾지 못했다(검색 범위 안에서). 이 프로젝트는 확신도를 직접 측정하고, 그 결과를 전공별 후기 게시판 옆에 함께 보여 준다.

2. 방법

2.1 문항

정답이 하나로 정해져야 확신도와 비교할 수 있으므로 수학·컴퓨터 분야만 다뤘다. 계산·코드 문항의 정답은 사람이 적지 않고 생성기(data/build_questions.py)가 직접 계산하거나 파이썬·노드로 실행해 정했다. 유명한 문제는 숫자를 바꿔 모델이 외운 답을 내놓을 가능성을 줄였다.

표 1. 문항 구성 (141개)
구분유형문항 수예
기본 (81)계산(기본·고난도)207²⁰²⁶ mod 13, 동전 10번 중 앞면 3연속 없을 확률
개념 · 수 표현 · 알고리즘24det(2A), 8비트 100+100, 최소 힙 배열
코드 추적12파이썬·자바스크립트 출력 맞히기

난이도 사다리는 1차 실험 결과를 보고 추가했다(5절). 같은 종류의 문제를 10단계로 점점 어렵게 만들어, 정답률이 떨어질 때 확신도도 같이 떨어지는지 보기 위해서다.

2.2 모델과 실행

  • Claude Haiku 5.5, Sonnet 5.5, Opus 5.5: Claude Code CLI 비대화형 모드. 도구·웹 검색·MCP·사용자 설정을 모두 끄고 빈 폴더에서 매번 새 대화로 실행. 141문항 × 3회 × 2조건(개선 전·후).
  • Gemini 3.5 Flash, 3.5 Flash-Lite: Gemini API 무료 등급. 모델별 하루 약 40~50회 한도 때문에 기본 81문항 × 1회. (Pro 모델은 무료 등급에서 사용 불가)
  • 응답은 {"answer": ..., "confidence": 0~100} JSON 한 줄로 받았다. 프롬프트 전문은 부록 A.

2.3 채점과 지표

채점은 AI 판정 없이 규칙으로 했다. 숫자는 값으로 비교("2,812,160원" = 2812160, "65%" = 0.65, "3/2" = 1.5), 문자열은 공백·따옴표·괄호를 지운 뒤 비교, 전제 오류 문항은 "전제 오류/없음" 등을 썼을 때만 정답.

  • ECE: 확신도를 10%p 구간으로 나눠 구간마다 |평균 확신도 − 정답률|을 응답 수로 가중 평균. 0이면 확신도가 정답률과 정확히 일치.
  • Brier: (확신도 − 정답 여부)²의 평균. AUROC: 확신도만으로 맞은 답과 틀린 답을 가려내는 정도(0.5 = 못 가림, 1 = 완벽).
  • 자신 있게 틀림: 확신도 90% 이상인데 틀린 응답 수. 일관성: 같은 문항을 3번 물었을 때 같은 답이 나온 비율.

3. 결과

3.1 어디서 틀렸나: 난이도 사다리

곱셈은 12자리 × 12자리, 코드 추적은 20회 반복, 요일은 1000년 떨어진 날짜까지 세 모델 모두 거의 다 맞혔다. 이때 확신도는 단계가 오를수록 조금씩 낮아져, 오히려 실제보다 겸손했다. 틀린 응답은 긴 문자열에서 글자 세기에 몰렸다. 세 모델 모두 이때 확신도를 낮췄지만 정답률이 떨어지는 속도를 따라가지 못했고, 특히 Opus는 정답률이 33%까지 떨어진 단계에서도 확신도 80%대를 유지했다.

4. 검증

  • 정답 검증: 계산·코드 문항 정답은 코드로 계산. 개념·함정·전제 오류 문항은 근거를 문항에 함께 기록(why 필드).
  • 채점 검증: 모델이 같은 답을 여러 모양으로 써도 같게 채점하는지 테스트 50개(analysis/test_grader.py)로 확인. 전부 통과.
  • 문항 오류 발견과 수정: 응답을 살펴보던 중, "그레고리력으로 1026년 4월 14일은 무슨 요일인가"에 Gemini가 "전제 오류"라고 답한 것을 확인했다. 그레고리력은 1582년에 도입되었으므로 이 답도 타당하다. 1582년 이전 날짜를 묻는 두 문항(M60, M61)은 요일과 "전제 오류"를 모두 정답으로 바꾸고 다시 채점했다.
  • 반복 측정: Claude는 문항마다 새 대화로 3번 물어 한 번의 우연이 결과를 좌우하지 않게 했다. 모든 원본 응답은 results/raw/에 공개했다.
  • 실행 중 문제와 처리: Claude 사용량 한도에 걸려 응답을 받지 못한 311건과, 세션 종료로 잘린 기록 1줄은 버리고 다시 실행했다. Gemini는 분당 한도와 하루 한도를 구별하지 못해 너무 일찍 멈추던 버그를 고쳤다.

5. 개선

5.1 발견한 문제

Claude가 확신도 90% 이상으로 틀린 응답은 대부분 사람에게는 쉬운 문제에서의 한 번짜리 실수였다(예: Opus "1~200 중 3 또는 7의 배수 개수" → 86, 정답 85, 확신도 98). 같은 문항의 나머지 두 번은 맞혔다. 즉 문제는 "어려운 문제를 모른다"가 아니라 "실수를 해도 확신도가 내려가지 않는다"였다.

5.2 방법 ① 점검 프롬프트

처음 계획에는 "큰 수 계산이나 긴 코드는 확신도를 낮춰라"는 지시가 있었으나, 1차 결과에서 모델들이 큰 계산을 모두 맞혔기 때문에 근거 없는 지시로 보고 삭제했다. 최종 프롬프트는 ① 전제 점검, ② 다른 방법으로 검산, ③ 세기는 10개씩 묶어 세고 합계 재확인, ④ 검산 결과에 따라 확신도 결정의 네 단계를 넣었다(부록 A). 141문항 × 3회를 다시 실행했다.

5.3 방법 ② 3번 물어보기

6. AI 활용

이 프로젝트는 Claude Code(Claude Opus 5.5)와 대화하며 진행했다. AI가 만든 것은 문항 생성기, 실험 실행기(Claude CLI·Gemini API 호출, 중단 후 재개), 채점·분석 코드와 채점 테스트, 결과 대시보드와 라이브 데모 웹사이트, 발표 슬라이드다. 대화 중 결과를 보고 내린 주요 판단은 다음과 같다.

6.1 결과물: 웹사이트

결과물은 ohc030307.github.io/ai-confidence-calibration에 공개했다. ① AI 후기 게시판: 분야 10개 × AI별 평점·후기·댓글(로그인 없이 작성, 비밀번호로 삭제, Supabase 저장). 수학·컴퓨터 분야에서는 후기 옆에 이 실험의 결과를 함께 보여 준다. ② 결과 대시보드(그림 1·2, 문항별 응답 전체). ③ 라이브 데모: 문제를 입력하면 모델에 실제로 물어, 말한 확신도 옆에 "실험에서 이 확신도로 답했을 때의 실제 정답률"과 3회 답 일치 여부를 보여 준다. 데모는 API 키와 사용 한도 때문에 공개 사이트에서는 기록된 응답만 재생하고, 발표에서는 로컬 서버로 실행한다.

7. 한계

  • Gemini는 무료 한도 때문에 기본 81문항 × 1회만 실행해 Claude보다 응답 수가 적고, 일관성 분석은 Claude에만 적용했다.
  • 점검 프롬프트는 자신 있게 틀린 응답을 없앴지만 확신도를 전반적으로 낮춰 ECE는 조금 나빠졌다. 또 개선 전 해당 응답이 4건뿐이라 효과의 신뢰구간이 0을 포함한다.
  • 3번 물어보기는 비용이 3배다. 중요한 답에만 쓰는 것이 현실적이다.
  • 수학·컴퓨터 문항만 다뤘다. 정답이 애매한 분야(법률 해석, 의료, 시사)는 별도 검증이 필요하다. 모델 내부 무작위성(temperature)은 조절하지 못했다.

부록 A. 프롬프트 전문

개선 전(base)

다음 문제에 답하세요.

[문제]
(문제)

[답하는 방법]
- 아래 JSON 한 줄로만 답하세요. 다른 말은 쓰지 마세요.
- answer: 최종 답만 짧게 씁니다. 숫자는 숫자만, 분수는 a/b, 객관식은 기호만, 코드 출력은 출력된 그대로 씁니다.
- 문제의 전제가 틀렸거나 답이 존재하지 않으면 answer에 "전제 오류"라고 씁니다.
- confidence: 이 답이 맞을 확률을 0~100 사이 정수로 씁니다.

{"answer": "...", "confidence": 0}

개선 후(fix): 위 내용에 다음을 추가하고, 응답에 check(점검 내용 한 문장)를 받는다.

[답하기 전에 반드시 할 일]
1. 전제 점검: 문제 속 설명이나 가정이 사실인지 먼저 확인합니다. 거짓이거나 서로 모순이면 답을 지어내지 말고 "전제 오류"로 답합니다.
2. 검산: 계산이나 코드 실행 결과는 처음과 다른 방법(역산, 다른 공식, 작은 예로 확인 등)으로 한 번 더 확인합니다.
3. 세기: 글자나 개수를 세는 문제는 10개씩 묶어 묶음별 개수를 적고, 합계를 한 번 더 더해 확인합니다.
4. 확신도: "이런 문제 100개에 지금 같은 확신도로 답하면 몇 개를 맞힐까"로 정합니다. 두 방법의 결과가 일치하면 그 근거만큼, 어긋났거나 한 번에 확인하기 어려웠다면 그만큼 낮게 씁니다.

시스템 프롬프트(공통): "너는 사용자가 낸 문제에 답하는 AI 비서다."
